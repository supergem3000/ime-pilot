# ime-pilot 架构治理与开发交接

更新日期：2026-10-31。

当前处于架构讨论阶段，本文记录设计目标、现有代码对应关系及后续建议；不代表重构已经实现。本轮范围是 ime-pilot 本体，暂不展开 IDEA 插件内部实现，也尚未开始鼠须管适配。

## 已明确的设计目标

本体按三个主要职责划分，并通过接口隔离具体实现：

1. **核心逻辑**：处理窗口信号和插件信号，管理规则、配置、请求调度，决定何时切到中文或英文，向控制器下发切换请求。
2. **系统信号捕获**：对接各操作系统，提供前台应用、窗口变化等信号。
3. **输入法控制器**：对接系统或具体输入法，实现中英文切换。

扩展目标是：**新增一种切换方案，主要工作集中在新增一个 package，提供中英文切换对接、支持系统声明和配置 UI 定义**。核心逻辑不应为每种新输入法增加分支，通用设置页也不应逐个硬编码方案的配置项。

这里的适配单位是“切换方案”，例如 Windows 微软拼音内部中英文切换、Windows 中文布局与英文键盘布局切换、macOS 中文与英文输入源切换，以及不同系统上的第三方输入法适配。一个通用方案可以服务多个输入法，不必每个品牌都建一个适配器。

## Switcher 的职责边界

Switcher 负责执行中英文切换，不负责判断插件是否有权控制某个应用，也不接收业务层的应用规则、插件会话或接管状态。

**不把“本次业务请求针对哪个前台应用”的 Target 加进统一 Switcher 接口。** 前台应用匹配、请求是否过期、是否应被新请求取消，属于核心处理链路。

某个系统 API 如果需要窗口句柄或线程信息，由适配器内部获取，或使用共享的平台辅助能力。原生调用需要上下文，不等于所有适配器都要暴露业务 Target。调用过程必要的原生有效性检查仍可留在适配器内部。

用户提出的执行能力是 `SwitchEn`、`SwitchCN`，另需声明支持系统。以下只是执行接口草案，`context.Context` 和具体命名尚未定稿：

```go
type Switcher interface {
    SwitchEn(ctx context.Context) error
    SwitchCN(ctx context.Context) error
}
```

支持系统可以通过方法或方案元数据表达，具体形式待定。不要直接把现有 `Snapshot`、`Apply`、状态轮询机制变成每种新适配器必须实现的公共契约；这些能力是否需要公开，应由实际调用需求决定。

## 一个适配器 package 应提供什么

| 内容 | 职责 |
| --- | --- |
| 方案信息 | 稳定 ID、展示名称、支持的操作系统 |
| 切换实现 | 按配置执行切英文、切中文 |
| 配置定义与校验 | 解释本方案的配置，检查字段及组合是否合法 |
| 配置 UI 定义 | 定义配置项、控件类型、说明和候选项来源 |
| 环境可用性 | 按需检查当前机器是否具备运行条件，与“支持该操作系统”区分 |

例如，macOS 输入源切换方案自己定义“中文输入源”和“英文输入源”两个下拉框，并提供系统输入源候选项；核心和通用 UI 不需要理解 `ChineseSourceID`、`EnglishSourceID` 的具体意义。

UI 定义归适配器，控件渲染归公共 UI 层。初期可以用少量声明式控件描述支持下拉框、文本框、开关和说明。动态候选项如何从 Go 传到前端、是否需要额外配置动作，属于待定接口细节。

不能一边说新增方案只需一个 package，一边要求开发者去中央前端文件新增方案专属页面和判断分支。复杂交互如果确实超出公共表单能力，再按真实需求扩展，不提前构建庞大的 UI 框架。

## 建议的组装和配置方式

以下是落地建议，尚未确定最终类型与目录名称：

- 区分“方案定义”和“配置后的执行实例”：未配置时也能展示名称、支持系统和配置表单，配置完成后再创建 Switcher。
- 应用组装入口集中注册方案；Go package 不会自动被发现，新增 package 后增加一处显式注册是合理成本，暂不引入动态插件加载。
- 公共配置保存所选方案 ID 和方案自己的配置数据；通用规则、暂停状态等继续由核心管理。
- 配置存储层负责读写、版本和持久化；适配器负责本方案配置的解释与校验，避免存储层持续增加输入法专属字段和条件。
- 公共 UI 从注册信息生成方案列表，从适配器定义生成表单；保存配置后，由应用组装逻辑创建或替换执行实例。

可以用结构体和函数完成方案定义、注册与构造，不必为了“可扩展”堆叠多层 Factory、Provider、Manager 接口。

建议依赖方向如下：

```text
系统信号捕获 ──┐
              ├─> 核心规则与调度 ─> Switcher 接口 <─ 具体适配器
插件信号入口 ──┘

具体适配器 ─> 提供方案信息、配置定义与 UI 描述
公共 UI    ─> 渲染描述、提交配置
应用组装   ─> 注册方案、加载配置、连接核心与具体实现
```

系统事件是对状态变化的描述，插件请求是切换意图，两者可以复用调度能力，但不必强行包装成一个万能事件模型。

当前主要调用关系：

```text
系统 Monitor -> desktop 桥接 -> Agent.Observe
插件 RPC -> 目标与接管校验 -> Agent.SubmitPlugin
                           ↓
                    Agent 调度与有效性检查
                           ↓
                    Backend 构造函数
                           ↓
                    core.Controller
                           ↓
                    Backend 查询、应用与验证
```

手动切换入口目前直接调用 `core.Controller`，与自动切换共享操作锁，并没有完全走同一条调度路径。

现有基础可以保留：自动化层已具备后端构造函数注入、队列与取消能力，核心执行代码不依赖 Wails，配置已有原子写入。无需为了分层全部推倒重来。

## 当前结构需要治理的地方

1. **平台捕获和输入法控制混在一起。** `internal/platform` 同时处理监听、枚举和切换，不利于同一系统增加多种控制方案。
2. **通用配置绑定 macOS 输入源方案。** `Config.MacOS` 直接保存中文和英文输入源，存储层还检查两者不能相同；这个限制属于输入源切换方案，不能用于同一输入法内部中英文切换。
3. **执行抽象绑定当前验证流程。** `Backend.Snapshot/Apply` 和 `SourceSelector` 服务于现有控制路径，不等于未来所有方案都应遵循相同状态模型和轮询方式。
4. **桌面组装和业务处理交织。** 核心规则及调度应可独立演进，桌面层主要承担生命周期、绑定和展示。
5. **尚无统一的方案注册及配置 UI 扩展机制。** 目前不同系统选定具体后端，尚未实现运行时展示和选择多种切换方案。

“切到中文/英文”是核心意图，适配器决定通过输入源切换还是输入法内部模式实现。当前 macOS 代码按配置的输入源 ID 判断中英文状态，并不代表已经读取或控制输入法内部模式。

## 必须延续的行为与约束

- macOS 插件请求已改为校验前台应用 PID，不校验具体窗口；当前方案已去掉辅助功能权限依赖，用户已确认关闭权限后 IDEA 仍能切回 ABC。
- 架构治理不能无意间重新引入 macOS 辅助功能权限；未来某个新方案如果确实有权限要求，应单独说明其原因，不能变成本体统一前提。
- 保留现有请求取消、过期检查和插件接管保护的业务效果，迁移时重新明确各自归属，避免仅为了简化接口直接删除行为。
- 不默认通过模拟按键实现切换；新增适配器采用什么机制，需要结合该方案的实际能力另行决定。
- 未经用户要求，不编写或运行单元测试；代码保持简洁，不添加无依据的兜底和接口层级。

## 后续建议顺序

1. 先定最小的方案定义、Switcher、配置 UI 描述和注册方式，用现有 macOS 输入源方案检验是否足够简单。
2. 把现有 macOS 输入源控制和 Windows IMM 控制分别迁入方案 package；系统信号捕获继续独立提供事件。
3. 调整通用配置与 UI，让方案拥有自己的字段和校验，公共层只负责存取、渲染和启用。
4. 接好核心调度与方案执行实例，核对手动切换、窗口自动切换和插件请求路径的行为。
5. 再适配鼠须管或其他输入法，用新增方案验证扩展点是否成立；不要预先假定 Rime 引擎相同就意味着各系统的控制接口相同。

验收扩展性的关键是：新增方案主要修改自己的 package 和一处注册，不需要改核心规则、系统窗口监听以及中央 UI 的方案判断分支。
